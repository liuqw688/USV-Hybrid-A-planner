# 搜索等待、末航点与MPC路径过期修复

## 原因与修改

原来的完整搜索在ROS单线程回调内运行。搜索耗时超过控制器的`path_timeout: 3.0`时，路径发布、船位接收与安全监测都被阻塞，MPC因此制动。静态搜索失败时也没有重新发布安全的旧路径。

现在完整搜索在独立副本上后台执行，主线程仍按`planner_frequency`处理实时输入、安全复验与发布路径。每个节点最多有一个后台搜索，不会堆积线程。没有安全旧路径时仍发布空Path停车，绝不通过延长控制器超时来忽略危险。

搜索结果发布前按照最新地图、目标船及本船位置复验。若用户改变目标，取消旧搜索并拒绝旧任务的迟到结果。海图变化不会被后台副本覆盖。启发缓存只有地图版本一致时才回收。没有采用速度/角速度补偿规划耗时的方法。

不同ROS话题没有跨话题到达顺序保证。完整全局航点列表晚于活动航点到达时，现在会补认活动索引，避免把下一航点误认为新任务并清空路径。

Hybrid动态模型在目标1m内可以结束搜索；MPC原来要求路径末端位于最终目标0.5m内才能终点制动。现在只对“局部路径末端”放宽到1.05m，活动航点与最终任务目标仍必须相差不超过0.5m，中间航点不会因此变成停车点。实际停车容差未修改。

## 配置与运行

- `search_time_limit: 3.0`：每次完整搜索的墙钟预算，包含启发场与宽弧优化。增大给困难场景更多计算时间；减小更快失败重试但可能找不到路径。`0`不限制，推荐只用于离线测试。备选搜索各自有预算，监测不会等待搜索完成。
- `fast_guided_connection: true`：普通主航道缓弯优先采用船模积分、安全核验的连续宽弧连接，失败再进入完整搜索。结果每50ms检查一次，避免额外等待1Hz定时器。
- `result_join_distance: 1.5`、`result_join_heading: 0.35`：迟到结果裁去已走前缀后与实测船位/艏向的接续门槛；不吻合就重搜，不伪造连接段。
- `planner_frequency: 1.0`：实时安全监测与路径刷新频率，不是强制每秒完整重搜。
- `path_failure_hold_time`：兼容旧配置，现在安全旧路径的续用由实时复验决定，不再按固定保持秒数决定。
- MPC的`path_timeout: 3.0`、`odom_timeout: 1.0`与静态地图`map_timeout: 0.0`保持不变。

修改后需停止旧的一键启动，再执行：

```bash
cd /home/l/work_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch channel_navigation_manager river_navigation.launch.py
```

如果还发生输入过期，警告会明确给出`path age=...`、`odometry age=...`或`map age=...`及对应限制。实际失联、危险路径或确实无解仍应停车，不能保证所有目标都有可行路径。

## 回归验证

本次三个相关包共60项算法/跟踪/航道回归全部通过（Hybrid 49项、MPC跟踪辅助4项、航道几何7项）。独立ROS通信回归在实际1Hz监测下通过：持续末航点失败搜索时安全路径最大消息间隔为1.010秒，低于MPC的3秒过期门槛；撤销任务后收到空Path。

算法回归包括：搜索预算退出后能继续尝试、后台副本不能覆盖新增障碍地图、终点误差0.8m时正确触发最终段判定而中间点仍不触发。

`test/test_path_freshness_ros.py`在独立ROS域173运行两个真实ROS节点的通信测试：先取得直线路径，再切换到狭窄水域内不可完成掉头的末航点，验证失败重试期间安全旧路径持续发布，最后撤销任务验证空路径停车通知。此测试不启动RViz，不改变用户运行域，也不等于真实河道全任务跟踪验证。

```bash
source install/setup.bash
/usr/bin/python3 src/hybrid_a_star_planner/test/test_path_freshness_ros.py
```
